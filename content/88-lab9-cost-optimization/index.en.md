## Overview

Your portfolio advisor is fully deployed, secured, governed, and running in a VPC. But in production, cost management is just as critical as functionality. FSI workloads can generate high volumes of interactions — advisory sessions, portfolio checks, compliance queries — and without careful tuning, costs can escalate quickly.

In this lab, you'll optimize your agent's cost profile by tuning session lifecycle, evaluation sampling rates, and monitoring token usage.

### What You'll Learn

- Configure session idle timeout and max lifetime
- Monitor token usage with CloudWatch Metrics Insights
- Tune evaluation sampling rate to balance cost and coverage
- Review memory retention settings
- Build a cost monitoring dashboard

### Why Cost Optimization for FSI

:::alert{header="FSI Cost Considerations" type="info"}
- **High-frequency advisory interactions** during market hours drive unpredictable invocation spikes
- **Regulatory retention requirements** (SEC Rule 17a-4, MiFID II) may conflict with cost-optimal storage settings
- **Budget governance** for agentic workloads requires visibility into token-level consumption
- **Chargebacks to business units** based on usage demand per-team tagging and monitoring
:::

## Step 1: Configure Session Lifecycle

Sessions keep agent state (conversation history, tool state) in memory. Idle sessions consume resources. Configure appropriate timeouts for your FSI workload:

:::alert{header="CLI Exception: Session Lifecycle Parameters" type="warning"}
Session lifecycle parameters are configured directly in `agentcore.json` — the `agentcore` CLI does not expose flags for these settings. You must edit the configuration file manually.
:::

Open `agentcore/agentcore.json` in Kiro's editor and add a `sessionConfig` block inside your runtime configuration:

:::code{language=json}
"sessionConfig": {
  "idleRuntimeSessionTimeout": 300,
  "maxLifetime": 3600
}
:::

| Parameter | Value | Default | Explanation |
|-----------|-------|---------|-------------|
| **idleRuntimeSessionTimeout** | 300s (5 min) | 900s (15 min) | Sessions close after 5 minutes of inactivity. For market-hours advisory sessions, 5 minutes is reasonable — advisors typically interact in rapid bursts. |
| **maxLifetime** | 3600s (1 hour) | 28800s (8 hours) | Maximum session duration regardless of activity. Shorter max lifetimes reduce the compliance exposure window. |

> **Cost impact:** Shorter idle timeouts free resources faster. If your agent handles 100 concurrent advisory sessions and you reduce the idle timeout from 15 minutes to 5 minutes, you free resources 3x faster during quiet periods between client interactions.

## Step 2: Monitor Token Usage with CloudWatch

Token usage is the primary cost driver for agentic workloads. Use CloudWatch Metrics Insights to understand your agent's token consumption.

Navigate to CloudWatch:

1. Open the [CloudWatch console](https://console.aws.amazon.com/cloudwatch/)
2. Go to **Metrics** → **All metrics** → **Bedrock-AgentCore**
3. Look for the following key metrics:
   - `InputTokenCount` — tokens sent to the model per invocation (system prompt + conversation history + tool results)
   - `OutputTokenCount` — tokens generated by the model per invocation (agent response + tool call parameters)
   - `InvocationCount` — total number of agent invocations

### CloudWatch Metrics Insights Query

Use the AWS CLI to query token usage directly from your terminal:

::::tabs{variant="container" groupId="os"}
:::tab{label="macOS/Linux"}
```bash
# View token metrics for the last hour
aws cloudwatch get-metric-statistics \
  --namespace "Bedrock-AgentCore" \
  --metric-name "InputTokenCount" \
  --start-time $(date -u -v-1H +"%Y-%m-%dT%H:%M:%S") \
  --end-time $(date -u +"%Y-%m-%dT%H:%M:%S") \
  --period 300 \
  --statistics Sum Average Maximum \
  --output table
```
:::
:::tab{label="Windows"}
```powershell
# View token metrics for the last hour
$startTime = (Get-Date).AddHours(-1).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ss")
$endTime = (Get-Date).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ss")

aws cloudwatch get-metric-statistics `
  --namespace "Bedrock-AgentCore" `
  --metric-name "InputTokenCount" `
  --start-time $startTime `
  --end-time $endTime `
  --period 300 `
  --statistics Sum Average Maximum `
  --output table

```
:::
::::

> **Tip:** For FSI cost allocation, tag your agent resources with business unit, team, and use-case tags. Use CloudWatch dimension filtering to break down costs per team and enable accurate chargebacks.

### Cost Estimation Rule of Thumb

:::alert{header="Typical Token Ranges per Invocation" type="info"}
| Metric | Typical Range | Cost Driver |
|--------|--------------|-------------|
| Input tokens | 1,000 - 5,000 | System prompt + conversation history + tool results |
| Output tokens | 200 - 1,500 | Agent response + tool call parameters |
| Tool calls | 1 - 3 | Gateway invocations (Lambda, API calls) |
:::

> **System prompt optimization:** If your input tokens are consistently high, review your system prompt length. A concise system prompt with the same behavioral instructions can reduce per-invocation costs by 20-40%. Every token in the system prompt is sent on every invocation.

## Step 3: Tune Evaluation Sampling Rate

In Lab 6, you configured 100% evaluation sampling for testing. In production, this is unnecessarily expensive — evaluate a representative sample instead.

::::tabs{variant="container" groupId="os"}
:::tab{label="macOS/Linux"}
```bash
# Check current evaluation config and runtime status
agentcore status

# Pause the existing evaluation config before reconfiguring
agentcore pause online-eval QualityMonitor

# Re-add the evaluation with a 20% sampling rate
agentcore add online-eval \
  --name QualityMonitor \
  --runtime PortfolioAdvisor \
  --evaluator Builtin.GoalSuccessRate Builtin.Correctness Builtin.ToolSelectionAccuracy \
  --sampling-rate 20 \
  --enable-on-create

# Deploy the updated configuration
agentcore deploy -y -v
```
:::
:::tab{label="Windows"}
```powershell
# Check current evaluation config and runtime status
agentcore status

# Pause the existing evaluation config before reconfiguring
agentcore pause online-eval QualityMonitor

# Re-add the evaluation with a 20% sampling rate
agentcore add online-eval `
  --name QualityMonitor `
  --runtime PortfolioAdvisor `
  --evaluator Builtin.GoalSuccessRate Builtin.Correctness Builtin.ToolSelectionAccuracy `
  --sampling-rate 20 `
  --enable-on-create

# Deploy the updated configuration
agentcore deploy -y -v

```
:::
::::

> **Cost impact:** Reducing sampling from 100% to 20% cuts evaluation costs by 80% while still providing statistically significant quality signals. For high-volume FSI workloads (1,000+ daily interactions), 10-20% sampling is standard practice.

### Sampling Rate Guidelines

| Daily Interactions | Recommended Sampling | Rationale |
|-------------------|---------------------|-----------|
| < 100 | 100% | Low volume — evaluate everything |
| 100 - 1,000 | 20-50% | Moderate volume — statistical significance at 20%+ |
| 1,000 - 10,000 | 10-20% | High volume — 10% provides ~100-200 daily samples |
| > 10,000 | 5-10% | Very high volume — 5% still gives 500+ daily samples |

## Step 4: Review Memory Retention

AgentCore Memory stores conversation events and extracted facts. Review retention settings to align cost with FSI compliance requirements.

Check your current memory configuration:

:::code{language=bash}
agentcore status
:::

Look at the memory configuration section in the output. Key retention parameters:

| Parameter | Default | Description |
|-----------|---------|-------------|
| **Event retention** | 30 days | How long raw conversation events are stored |
| **Record retention** | Longer | How long extracted semantic records (client preferences, risk tolerance) are kept |

:::alert{header="FSI Retention Considerations" type="warning"}
Financial services firms may have conflicting requirements: regulatory mandates such as SEC Rule 17a-4 and MiFID II may require 3-7 years of communication retention, while cost optimization favors shorter retention. Work with your compliance team to determine the right balance. AgentCore Memory's retention settings may need to be supplemented with long-term archival storage for regulatory compliance.
:::

> **Tip:** Use memory expiry strategically:
> - **Conversation events** (30 days default): Sufficient for active advisory relationships and recent context
> - **Extracted facts** (longer retention): Client preferences, risk tolerance, and portfolio strategy should persist well beyond 30 days
> - For regulatory archival, export conversation logs to S3 with lifecycle policies *before* AgentCore Memory expiry

## FSI Cost Optimization Best Practices

:::alert{header="Production Checklist" type="info"}
- **Right-size session timeouts** — Match to actual usage patterns: shorter idle timeout during market hours (rapid advisory bursts), longer during end-of-day analysis workflows
- **Evaluation sampling** — Start at 20%, increase if quality issues are detected, decrease when quality is stable
- **System prompt optimization** — Every token in the system prompt is sent on every invocation — keep instructions concise without sacrificing clarity
- **Memory tiering** — Use AgentCore Memory for active data; archive to S3 with lifecycle policies for regulatory retention
- **Cost allocation tags** — Tag all resources (runtime, gateway, memory) for accurate chargeback to business units
- **Budget alerts** — Set CloudWatch billing alarms to detect unexpected invocation spikes during market volatility events
:::
